## 真实文件

用户提供的混排投标 PDF：274 页、14,546,045 字节。测试允许查看正文；本文及导出证据仅保留数量、耗时、校验结果和哈希，不包含正文、真实名称或金额。

- Java → HTTP → Python/Paddle 完整读取 274 页，87 页进行了 OCR，输出 187,695 字符，覆盖缺口 0，页码顺序正确。用时 956.329 秒，约 15 分 56 秒。
- 最终版本读取已持久保存的检查点，用时 0.825 秒；与首次读取的结果逐项相同，未重复调用 OCR。此项验证共享读取器的恢复能力，不代表预算、合同已新增逐页 DM8 持久化功能。
- 六张真实扫描页，包含侧向截图、证照和盖章正文：单路 430.334 秒、两路 289.440 秒、四路 215.795 秒。各路提取文字哈希完全相同，四路比单路减少约 49.9% 耗时。此比例仅属于六页对照，整份文件没有另跑单路基线，不推算整份提速比例。
- 整份读取期间 OCR 子进程峰值 RSS 合计 9,724,837,888 字节，约 9.1 GiB。456 次 AI 健康、后端健康和页面检查全部 HTTP 200，观测最大响应约 5.4 毫秒；监测从文件处理途中启动，不覆盖最初几分钟。

真实模型抽测：从已完成读取的六段正文、共 4,991 字符中，经现有采购提取接口取得 8 条信息，涵盖项目名称、项目编号、采购人、供应商及报价。每条摘录和值都能回到对应原文，29.7 秒完成。结果在测试环境人工查看核对，实际信息不写入导出证据。此项是代表性正文抽测，不是整份 18.8 万字的完整采购审查或报告质量验收。

## 实现

共享 Java 读取器先读取原生文字，再对扫描页和大图混排页 OCR。全局信号量在提交工作前获得，跨文件共享并发上限。PDFBox、结果集合、检查点仅在所属调用线程修改；工作线程持有其单页临时 PDF，调用结束后才删除。按完成顺序接收结果并保存检查点，最终输出依照原页码排序。

新增 Python 进程池使用独立 ProcessOcrAdapter，不共享 Paddle 实例。启动时综合 affinity、可见 cgroup v2 各级 CPU/内存限制和可用内存选择实际进程数，未知时保留单路。无控制器文件的子组继承父组限制；不可读、非法或无法定位的进程组不会授权扩容。

四路是 26 的配置上限。内存参数是准入规划估算，不是 OS 对 RSS 的硬约束，不承诺运行中动态伸缩。配置和边界见 `docs/ocr-resource-configuration.md`。

侧向页面实测超过 120 秒，因此共享读取器等待 OCR 槽位的上限从 120 秒调整为 1900 秒，与既有 OCR HTTP 等待边界对齐，避免其他文件仅因排队提前失败。未改变单次模型调用时限。
