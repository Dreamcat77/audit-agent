# 后端 B 已知问题与后续验证清单（2026-08-24）

## 1. 文档目的

本文件记录后端 B 当前已合入 A+B 共享基线的 F01/F03 相关已知问题、验证边界和后续建议。

本次 A+B 基线整合的目标是保留双方已有功能并形成共同开发基线，因此没有在整合阶段重构后端 B 的业务语义。下列问题在合入 `main` 后继续保留为后续事项。

重要边界：当前仓库尚未选择自动数据库迁移框架，`db/dm8/Vxxx__*.sql` 由受控流程手工按序执行。因此，只要暂不执行 F01/F03 对应的新 DM8 迁移、也不在真实 `local-dev` / `dev29` / `customer` 环境调用 F01/F03 的 DM8 路径，这些数据库问题不会影响 `local` Profile、F02、Contract/ReviewSession 现有本地功能。但在真实 DM8 部署前必须处理 P0 项。

本次合并冲突与处理决策见：[后端 A 与后端 B 基线合并冲突与决策复盘](./后端A与后端B基线合并冲突与决策复盘-2026-08-24.md)。

## 2. P0：真实 DM8 部署前必须处理

### 2.1 F01 V007/V008 重复字段

当前：

- `db/dm8/V007__f01_material_review.sql` 创建 `BUDGET_REVIEW_ITEM` 时已经包含：
  - `SUBJECT_CODE`
  - `SUPPLIER_NAME`
  - `APPROVAL_SUBJECT_CODE`
  - `APPROVAL_SUPPLIER_NAME`
- `db/dm8/V008__f01_material_check_fields.sql` 又对同一表执行四个同名 `ADD COLUMN`。

风险：如果在新库按 `V001 -> ... -> V008` 顺序执行，V008 可能因重复列失败。

建议：在真实 DM8 迁移前由后端 B 确认该历史的正确演进方式，并补一条能够验证 V006-V008 顺序执行的真实 DM8 证据。

### 2.2 F03 尚未纳入正式版本化迁移链

当前 F03 DDL 位于：

`backend/src/main/resources/sql/f03_blacklist_ddl.sql`

但 `Dm8BlacklistSupplierRepository` / `Dm8BlacklistAlertRepository` 在 `local-dev`、`dev29`、`customer` 会使用 `BLACKLIST_SUPPLIER` 和 `BLACKLIST_ALERT`。

风险：若仅执行当前 `db/dm8` 的版本化 SQL，新库不会自动具备 F03 表；真实调用 F03 时会失败。

建议：在 F03 进入真实集成环境前，把现有 F03 DDL 纳入正式版本化迁移，或明确由环境初始化脚本负责，并记录真实 DM8 验证证据。

### 2.3 `DmJdbcDriver18` 尚未完成真实 DM8 运行验证

A+B 新基线 POM 当前包含：

`com.dameng:DmJdbcDriver18:8.1.3.140`

历史 F02 本机真实 DM8 验证使用过 DmJdbcDriver11；本次整合只验证了 Driver18 的依赖解析、编译和打包，没有验证现有 F01/F02/F03/ReviewSession DM8 Adapter 在真实 DM8 上的完整行为。

影响：这是共享基础设施风险，不只影响 F01/F03。

建议：下一次 `local-dev` / `dev29` 提测前，用当前最终 JAR 和 Driver18 对真实 DM8 做一次共享回归。

## 3. P1：F01/F03 正式投入使用前应复核

### 3.1 F01 正式迁移中包含演示数据

`V006__f01_budget_approval.sql` 当前在建表后直接插入固定采购需求、预算科目、供应商和 UUID 测试数据。

风险：若直接用于共享或客户新库，会把演示业务数据写入正式 schema。

建议：真实部署前把演示 INSERT 移至 `db/dm8/demo/` 或独立种子数据文件，正式迁移只负责 schema。

### 3.2 F01 材料任务依赖临时文件路径

当前 Budget 材料链会保存 `TEMP_FILE_PATH`，并使用 Java 临时文件及进程内映射继续审查。

风险：Java 重启、临时目录清理或文件丢失后，已持久化任务可能无法继续处理，需要重新上传材料。

这不影响当前 `local` 编译/测试，也不影响不调用该材料链时的其他模块。

建议：后续由后端 B 决定是把“上传 + 解析 + 审查”收敛为一次性同步流程，还是接入共享 `FileStoragePort` / 持久化文档模型。

### 3.3 F01 两条金额校验路径语义不一致

当前观察到：

- `BudgetCheckService` 使用数值相等语义比较预算金额和实际金额；
- `BudgetReviewService` 的材料审查路径按“申报金额不超过预算金额”判断通过。

这可能是两个不同业务入口，也可能是规则不一致。

建议：由后端 B / 产品明确两条 API 的业务语义，并在后续任务中增加边界用例，避免同一业务事实通过不同入口得到相反结论。

### 3.4 F01 科目模糊匹配与供应商校验需产品确认

当前 F01 材料审查包含：

- Levenshtein 模糊匹配；
- 供应商名称一致性检查。

这些代码本次整合原样保留，没有重新定义产品语义。

建议：后续确认模糊匹配是“自动通过”还是“候选/人工确认”，并确认供应商校验是否属于 F01 正式范围。

### 3.5 F01/F03 写操作的长期操作审计、幂等与事务边界

F02 / ReviewSession 已建立较严格的长期操作审计、幂等和事务规范；F01/F03 当前实现没有在本次整合中按同一标准重构。

建议：在真实环境启用写接口前分别复核：

- F01 预算结果写入；
- F01 材料任务/明细写入；
- F03 黑名单条目新增/删除；
- F03 告警生成/处理。

重点确认 Operation Audit、重复提交、并发更新和失败回滚语义。
