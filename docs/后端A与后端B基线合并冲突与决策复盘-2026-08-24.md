# 后端 A 与后端 B 基线合并冲突与决策复盘（2026-08-24）

## 1. 文档目的

本文件用于记录 2026-08-24 后端 A 与后端 B 两条开发线合并为共同 `main` 基线时，实际遇到的冲突、处理原则、最终决策、验证结果和保留风险。

这不是新的架构设计文档，也不是对后端 B 业务代码的重构说明。它记录的是一次已经完成的 integration 事实，便于后续 F04-F15 并行开发时理解为什么当前 `main` 会同时存在 F01/F02/F03、四个 Runtime Profile、统一 Security/CORS、共同前端入口及新的 DM8 迁移编号。

后端 B 当前遗留问题及后续验证要求见：[后端 B 已知问题与后续验证清单](./后端B已知问题与后续验证清单-2026-08-24.md)。

## 3. 总体合并原则

### 3.1 业务专属模块优先保留原实现

本次没有借 integration 重构业务语义。

后端 A 已有业务模块保持：

- `contract/**`
- `review/**`
- Contract Catalog
- ReviewSession / ReviewDocument / MaterialBinding
- FileStorage / recovery
- F02 确定性审查

后端 B 已有业务模块保持：

- `budget/**`
- `blacklist/**`
- F01 Budget API、材料解析和审查
- F03 黑名单匹配、告警和维护
- 对应 local Repository、DM8 Adapter、Mapper、PersistenceRow 和测试

合并阶段没有重新定义 F01 的金额规则、科目模糊匹配、Supplier 校验、BudgetReviewTask、ProcurementDemand 或 F03 告警语义。

### 3.2 公共区域不采用简单 ours/theirs

以下共享区域按照“以最新 main 的结构和安全基线为底，加入后端 B 真正需要的能力”处理：

- `backend/pom.xml`
- `common/**`
- `security/**`
- `application*.yml`
- `integration` 下共享 Adapter
- 前端 `api/**`
- `App.tsx`
- `main.tsx`
- shared styles
- README / AGENTS / architecture / source-baseline

最终目标是功能并集，而不是整文件取一方覆盖另一方。

## 4. 具体冲突与最终决策

## 4.1 DM8 migration 编号冲突

### 冲突

合并前，后端 A 已经占用：

- `V004__contract_review_session.sql`
- `V005__contract_review_session_soft_delete.sql`

后端 B 原 F01 分支同时存在：

- `V004__f01_budget_approval.sql`
- `V005__f01_material_review.sql`
- `V006__f01_material_check_fields.sql`

如果直接合并，会出现全局 migration 版本号冲突。

### 决策

保持后端 A 已经进入主线的 V004/V005 不变，仅将后端 B 的 F01 migration 顺序平移：

| 后端 B 原版本 | 合并后版本 |
| --- | --- |
| `V004__f01_budget_approval.sql` | `V006__f01_budget_approval.sql` |
| `V005__f01_material_review.sql` | `V007__f01_material_review.sql` |
| `V006__f01_material_check_fields.sql` | `V008__f01_material_check_fields.sql` |

本次重编号的目标只是消除全局编号碰撞，不借机重写后端 B 的 schema 业务内容。

### 保留风险

- V007 已包含 V008 再次 `ADD COLUMN` 的四个字段，真实顺序迁移仍需后续修正。
- F03 DDL 仍位于 `backend/src/main/resources/sql/f03_blacklist_ddl.sql`，尚未纳入正式 versioned migration。
- V006 仍包含演示数据 INSERT。

这些问题均已单独记录在后端 B 已知问题文档中。

## 4.2 Runtime Profile 冲突

### 冲突

合并前 `main` 正式支持：

- `local`
- `dev29`
- `customer`

后端 B 引入了一套 `local-dev`，用于本机连接真实 DM8、Redis Session，同时使用 Fake AI/OCR。

### 决策

新共享基线正式保留四个 Runtime Profile：

- `local`
- `local-dev`
- `dev29`
- `customer`

`ActiveProfileGuard` 更新为四选一，并保留“必须且只能激活一个 Runtime Profile”的约束。

`local-dev` 同时加入相关 DM8 Adapter、ReviewSession Adapter、Operation Audit fail-closed 配置和 Profile 测试。

### 配置安全处理

后端 B 原 local-dev 配置和启动脚本中的环境差异统一改为环境变量注入：

- `AUDIT_DB_URL`
- `AUDIT_DB_USERNAME`
- `AUDIT_DB_PASSWORD`
- `AUDIT_REDIS_HOST`
- `AUDIT_REDIS_PORT`
- `AUDIT_REDIS_PASSWORD`
- `AUDIT_FILE_STORAGE_ROOT`

没有把固定数据库地址、真实账号或密码带入新的 `main`。

## 4.3 Security / CORS 冲突

### 冲突

后端 A 主线已经需要：

- Session Cookie
- CSRF
- RequestId
- ReviewSession DELETE 请求
- 现有 401/403 处理

后端 B 新增：

- F03 `PUT /api/v1/blacklist/alerts/{id}/process`
- Springdoc / Swagger UI
- F01/F03 新 API

后端 B 原安全配置只覆盖 GET/POST/OPTIONS，而后端 A 已经需要 DELETE。

### 决策

最终 Security 保持 Session + CSRF 架构不变，同时扩展：

- Swagger UI / `/v3/api-docs/**` 放行
- CORS Methods 合并为：`GET / POST / PUT / DELETE / OPTIONS`
- 保留 `Content-Type`
- 保留 `Idempotency-Key`
- 保留 `X-CSRF-TOKEN`
- 保留 `X-Request-Id`

因此：

- ReviewSession DELETE 能力未回退；
- F03 PUT 能力被纳入；
- F01/F03 不需要引入 JWT 或新认证体系；
- 原 Session/CSRF 认证模型保持不变。

对应 CORS 集成测试新增 F03 PUT preflight 场景。

## 4.4 GlobalExceptionHandler 冲突

### 冲突

后端 A 主线已有：

- `SafeExceptionDiagnostics`
- 405 Method Not Allowed
- 413 Payload Too Large
- FlowDebug
- 现有统一业务异常和安全日志

后端 B 为 F01 multipart 上传补充了：

- `MissingServletRequestPartException`
- `MultipartException`

### 决策

没有用后端 B 的整个 Handler 覆盖主线，而是在后端 A 现有 Handler 上增量加入 multipart 400 处理。

因此主线的 SafeExceptionDiagnostics、405、413 和既有异常结构都被保留。

### 保留风险

当前全局 multipart 400 文案仍是“预算材料上传请求无效”，对未来 Contract 等其他 multipart 场景不够中性。这是公共文案问题，但不影响本次基线合并。

## 4.5 Maven / POM 依赖冲突

### 冲突

后端 B 新增运行依赖：

- `com.dameng:DmJdbcDriver18:8.1.3.140`
- Springdoc WebMVC UI 2.8.9
- Apache POI 4.1.2
- PDFBox 2.0.30

后端 A 主线已有 Web、Security、MyBatis、Redis、Spring Session、Tracing 等依赖。

### 决策

采用依赖并集：

- 不删除 main 已有依赖；
- 加入后端 B 四项依赖；
- 保持 Java 17 和 Maven Enforcer 规则不变。

POI 对应 F01 Excel/XLSX parser；PDFBox 对应文本型 PDF parser；Springdoc 对应 OpenAPI UI；DmJdbcDriver18 进入 A+B 新 POM。

### 保留风险

`DmJdbcDriver18` 仅完成 Maven 依赖解析、编译和打包，尚未完成当前 A+B 最终构建在真实 DM8 上的运行验证。因此它被记录为共享基础设施风险，而不是 F01 单模块风险。

## 4.6 前端共享文件冲突

### 冲突

后端 A 主线前端已经包含：

- AuthProvider / AuthGate
- Contract Catalog
- Contract Review Workspace
- ReviewSession Workspace

后端 B 分支新增：

- `BudgetCheckPage`
- `BlacklistAlertPage`
- F01/F03 API
- F01/F03 TypeScript DTO 类型
- 相关导航入口

双方同时修改 `App.tsx`、`main.tsx`、`api/audit.ts`、`api/types.ts` 等共享文件。

### 决策

最终前端做功能并集：

- `main.tsx` 继续保留 `AuthProvider + AuthGate`；
- `App.tsx` 同时挂载 Contract/ReviewSession、Budget、Blacklist 页面；
- `api/audit.ts` 同时保留既有 API 和 F01/F03 API；
- `api/types.ts` 增加 F01/F03 类型，不删除其他共享类型；
- Budget/Blacklist 专属页面保留后端 B 原实现。

最终生产构建通过。

## 4.7 配置文件冲突

### `application-local.yml`

- JDBC/Redis 自动配置排除

## 4.8 DM8 Adapter Profile 扩展

为了让 `local-dev` 真正具有与 dev29/customer 相同的 DM8 业务 Adapter 能力，相关 `@Profile` 从：

`dev29 / customer`

扩展为：

`local-dev / dev29 / customer`

涉及的共享 Adapter 包括但不限于：

- Contract Repository
- Contract ReviewSession Repository
- ReviewDocument / MaterialBinding Repository
- User / Login Audit / Operation Audit
- Idempotency
- F01 Budget Repository
- F03 Blacklist Repository

该修改属于 Profile wiring 整合，不改变各业务 Repository 的领域行为。

## 7. 新的共同基线定义

PR #9 合并后，`main` 不再是后端 A 单独基线，而是后端 A + 后端 B 的共同执行基线。

当前 `main` 至少包含：

- F01 Budget；
- F02 Contract deterministic review；
- F03 Blacklist；
- Contract Catalog；
- ReviewSession / Document / MaterialBinding；
- FileStorage / Recovery；
- Auth / Session / CSRF；
- RequestId / Trace / Operation Audit；
- DM8 / Redis / FastAPI Adapter 边界；
- React/Vite 共享前端；
- `local / local-dev / dev29 / customer` 四 Profile。

后续任何 F04-F15 feature 都应从这个最新 `main` 创建，而不是继续以旧 `13c98d3` 或未合入 feature 为基础。

## 8. 后续 A/B 并行开发规则

为避免再次出现同模块互相等待和大规模 merge 冲突，后续采用以下规则：

1. **`main` 是唯一共享集成基线。**
2. **业务专属目录由对应 feature owner 优先维护。**
3. **两个 feature 不通过互相 merge 未合入分支来获取共享代码。**
4. **如果两个 feature 同时需要修改 Shared Core，先做一个小型 prerequisite PR 合入 main，再继续各自开发。**
5. **shared/common/security/config/frontend shell 发生冲突时，以最新 main 为结构基础做功能并集，不机械 Accept Current/Incoming。**
6. **DM8 migration 编号全仓库统一分配，创建前先检查最新 main 的最大版本。**
7. **已有业务设计问题不在 integration 阶段偷偷重构，单独建立 review/refactor 任务。**
8. **新 feature branch 从最新 main 创建，并在 PR 前做全量后端回归和前端 production build。**

## 9. 对后续 F04/F06/F08 的直接影响

从本次合并之后：

- F04 可以直接在已经存在的 `budget` 模块和 F01 基础上开发，不再需要单独 merge 后端 B 的 F01 feature；
- F06 开发前要注意当前 F01 的 `ProcurementDemand` 仍位于 `budget`，不要未经讨论就复制或移动该模型；
- F08 可以基于当前稳定 Contract Core 开发，不需要等待 F07/F09 业务分支，只要大家共同依赖最新 main；
- 所有新增 migration 必须从最新 main 当前最大版本之后继续编号，并先确认是否与并行开发占号冲突。

这份文档作为 2026-08-24 A+B 合并的历史记录；未来架构变化应新增 ADR、follow-up 或新的 merge 记录，不应回写篡改本次决策事实。
