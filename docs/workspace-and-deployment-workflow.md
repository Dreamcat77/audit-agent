# 工作区与部署工作流

## 唯一源码位置

本地唯一工作区：`E:\audit-agent`。代码目录为 `backend`、`frontend`、`services\audit-ai`、`db`、`scripts`、`tools`、`docs` 和 `test-materials`。不要在 `deliverables`、`.runtime`、`.backups` 或临时目录中直接开发；这些目录中的副本、构建结果和证据不能自动视为最新源码。

当前工作区在 2026-11-12 检查时没有 `.git` 元数据。GitHub 的远端提交、本地分支和工作区源码是否一致均未验证。进行 Git 集成或推送前，先恢复/确认正式 checkout 与正确 remote，逐项比较基线和工作区差异；不能因历史文档提及过某个分支或 commit 就推断它仍是当前值。

日常不要在仓库根目录堆放临时日志、截图、压缩包和单次构建目录。源代码、可复用测试材料和维护文档分别放在上述目录；本地保护快照保留在 `.backups` / `_protected-backups`；测试运行缓存放 `.runtime`。清理之前先检查引用和用途；未知用途的材料移入 `本地归档` 并记录，不直接删除。

## 环境角色

| 环境 | 用途 | 证据要求 |
| --- | --- | --- |
| 本机 `E:\audit-agent` | 唯一源码、测试和制包工作区 | 构建与测试要记录命令、JDK/Node/Python 版本和退出结果。 |
| 26 | 内部测试服务器 | 不是甲方环境。远程部署和浏览器/API测试需记录实际 release、服务状态、JAR/index/资源哈希以及三模块实测范围。不可达时标记 `NOT VERIFIED`，不根据预期状态推断。 |
| 甲方现场 | 内网既有安装，模型/数据库/网络均以现场事实为准 | 本机和 26 通常不可直接访问。准备离线更新包和只读脱敏工具；需要客户执行时提供明确的一条命令。包内代码、26测试和仿真材料不能替代现场验收。 |

主机、SSH 账号凭据、数据库账号、模型 Token、模型 URL 和客户真实网络地址不写入仓库。使用当轮授权和本机受保护的凭据源。文档可以使用环境名 `26`、`customer`，不能写密码或让脚本回显密钥。

## 代码与测试

1. 先读 `AGENTS.md`、本指南、`DEPLOYMENT-MEMORY.md` 最新记录和相关模块 QA 证据；确认这些证据是否仍然对应当前版本。
2. 后端：

   ```powershell
   cd E:\audit-agent\backend
   .\mvnw.cmd clean verify
   ```

3. 前端：

   ```powershell
   cd E:\audit-agent\frontend
   npm.cmd run build
   node --experimental-strip-types --test <本次涉及的测试文件...>
   ```

   当前 `package.json` 只有 build/build:customer/dev，没有 `test` script；按改动范围显式列出相关测试文件，不运行不存在的 `npm test` 命令，也不把测试跳过写成通过。
4. Python AI/OCR：使用已有 Python 3.11 虚拟环境，不覆盖工作区或系统 Python。先查 `pyproject.toml`、项目测试配置和现有虚拟环境，再运行相关 pytest。
5. 共享解析链路变化至少覆盖预算、采购、合同。分别区分单元、浏览器、26真实 HTTP/数据库、客户现场验证；Fake/Mock 结果不能写成真实集成通过。

## 26 测试流程

26 用于内部测试和故障复现，不视为生产环境。每次远程操作前先检查服务器可达性、当前实际发布目录/版本、服务状态、活动任务和磁盘容量。不要因为更新包版本新就直接覆盖；先保留业务数据和模型配置，且不擅自清库或删任务。

部署后至少检查：

- `GET /api/v1/health` 及前端页面/API资源加载；
- 管理员与预算、采购、合同角色的菜单和数据隔离；
- 预算、采购、合同各至少一条上传到结果、历史重开、原文查看的用户路径；
- OCR/模型服务实际状态与错误日志；
- 运行服务对应 release、JAR SHA256、前端 index/资源哈希与计划制品一致。

测试数据库和文件目录可能含用户已有材料。只有用户明确指定的记录可以测试后清理；默认保留并优先用新合成材料测试。26不可达时只完成本地工作和诊断包，写明 `NOT VERIFIED`。

## 甲方更新包

当前现场执行步骤以 [部署运行手册](runbook/customer-deployment-current.md) 及同步的 `现场工作区/部署文档.txt` 为准；`customer-offline-deployment.md` 的旧版本章节只供历史追溯。维护现场路径时注明是实测、安装器约定还是配置待查，不从26复制成现场事实。

新包统一放在 `现场工作区\更新包`，每次使用未占用的新版本号和新目录，不覆盖历史包。默认离线更新包面向麒麟 V10 SP3 2403 aarch64 的既有安装，不包含 JDK、Python、数据库或系统软件，不修改现场密钥和连接配置。

当前完整包构建器为 `tools\build-customer-v10.py`。打包前必须：

- 用 JDK 17 完成 Maven `clean verify`，并按当轮源码重建前端；
- 显式指定最终 JAR、前端 dist、经过哈希核验的模型目录和目标架构；
- 用新版本号构建到新的临时目录，核验 package inventory、源/包 manifest、tar SHA256、脚本 LF/syntax、Java class major 61 和离线模型完整性；
- 核对版本、改动文件和测试证据。工作区没有 Git 元数据时标记 `WORKSPACE-SNAPSHOT` / `HAS_UNCOMMITTED_FILES`，不能填写虚构 commit；
- 只把实际已做的验证写进包和部署记录。26 未部署、甲方未执行时分别标为 `NOT VERIFIED`。

现场通常只需按包内说明验证 SHA256、解压到新目录并运行 `sudo bash update.sh`。不要额外加入未经项目运行手册要求的备份证明、数据库结构判定或人工输入步骤；但更新包已有的必要数据库 preflight/结构漂移检查不能被擅自绕过。执行遇到阻断时，先收集脱敏日志和具体 `reasonCode`，保留现场状态，不重复执行可能非幂等的 DDL。

正式更新已包含预检，不强制重复运行`--check`。当前v28d不要求恢复JSON，也不自动备份数据库/业务文件。任务行状态不再作为部署门槛；先停止后端和AI两个服务、确认其工作进程退出，再做增量结构和版本切换。保留任务、文件和结果，不自动改写UNKNOWN、不清库、不全局结束Python。旧ProcurementUnblock工具属于历史维护路径，不是正常更新的前置步骤。

若现场已上传大包，而只需修复部署器，应优先交付小修复脚本，明确目标目录并自动继续原更新；避免重新上传相同应用载荷。修复脚本需能重复执行并正确同步清单。部署器变更做停止进程、失败恢复、只读模式和载荷一致性等专项回归；应用载荷未变时不为了修改部署脚本重复构建全应用。新交付使用新文件名，不改写旧压缩包；仅更新工作区文档时不重新封包。

## 日志和隐私

解析诊断只导出固定事件、阶段、错误类别、状态、耗时、文件字节/页数/文本长度等统计。禁止导出原始日志消息、文件正文、原文件名、项目名、单位/人员名、模型提示词/回答、HTTP 请求体、账号/密码、Token、完整连接串和客户 IP。能在现场本机定位的原始日志不打包，只将严格 allowlist 结果传回。

先用 `scripts\collect-ai-diagnostics.sh` 或相应 `tools\*diagnostics\run.sh` 的只读采集器；检查采集包中的每个字段和 hash 后再传回。采集“零条事件”只代表当前范围没有可导出的诊断事件，不能证明文件未上传或系统没有报错。
